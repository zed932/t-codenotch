# План очистки Codenotch для корпоративного использования

Дата: 2026-09-27. Исследован локальный checkout `07ba1db`.
Статус: этапы 2–4 выполнены, этап 5 выполнен частично (см. «Протокол проверок»). Этап 6 ждёт описания корпоративного источника.

## Протокол проверок (2026-09-27)

Выполнено на Xcode 26.1.1, macOS 26:

- `make test`: сборка без предупреждений в коде проекта, 10 unit-тестов модели и хранилища проходят.
- `make release && make verify`: единственный entitlement — `com.apple.security.app-sandbox`; нет `get-task-allow`, сетевых и файловых прав, нет `Contents/Frameworks`.
- `otool -L`: только системные Foundation, AppKit, SwiftUI, Combine, CoreGraphics и Swift runtime. SwiftPM-пакетов в проекте нет.
- `nm -u`: нет импортов URLSession, NWConnection, socket/connect, Process/posix_spawn, SecItem, sqlite, WebKit.
- `strings`: нет URL, упоминаний Keychain, `.claude`, `.codex`, Cursor, Sparkle.
- Запуск Release: процесс стартует, `lsof -i` не показывает сетевых сокетов.

Не проверено: внешний вид notch и поведение наведения (скриншот из агентской среды недоступен), сон/пробуждение, долгий запуск под сетевым монитором, сборка без доступа к публичным реестрам (сейчас она не требует скачиваний).

## Решение

Выделить минимальное приложение для отображения лимитов. Первый результат — автономный UI с явно обозначенными демонстрационными данными, без сети, чужих учётных данных, серверов и запуска команд. Второй, отдельный этап — единственный адаптер согласованного источника корпоративных лимитов.

Не сохранять универсальную систему интеграций с выключенными переключателями: ненужные реализации, зависимости и пользовательские действия должны отсутствовать в поставляемом коде и сборке. Без корпоративного источника приложение сможет показывать только демонстрационные или вручную введённые значения, а не реальные лимиты.

Целевая ОС подтверждена пользователем: только macOS. Windows-порт не дорабатываем; в минимальном корпоративном дереве удаляем его вместе со сборочными сценариями. Сведения о Windows ниже оставлены только как часть исходной инвентаризации.

## Структура и стек

- `Sources/App/`: запуск приложения, связывание компонентов в `AppDelegate.swift`, меню, обновления, команды терминала.
- `Sources/Notch/`: окна, положение у края экрана, несколько мониторов, анимации и модель UI.
- `Sources/Features/` и `Sources/DesignSystem/`: кольца лимитов, карточки, визуальные элементы, цвета и типографика.
- `Sources/Model/`: снимки лимитов, статусы, хранилище с опросом провайдеров, архив, уведомления. Здесь есть и общие модели, и специфичные для провайдеров структуры.
- `Sources/Providers/`: 89 файлов; API-клиенты, чтение credentials, web-сессии, CLI, парсеры, модели аккаунтов и иконки. Удалять папку целиком до переноса общих типов нельзя.
- `Sources/Sessions/`: 28 файлов; наблюдение за агентами, сессиями и процессами, переход к терминалу, локальные метрики и relay.
- `Sources/PhoneLink/`: 11 файлов; сервер, pairing, криптография, хранение секретов, передача снимков телефону.
- `Sources/Settings/`: настройки внешнего вида вместе с настройками провайдеров, аккаунтов и интеграций.
- `Tests/`: Swift unit-тесты моделей, UI-поведения, провайдеров, авторизации и других компонентов.
- `project.yml`, `Makefile`, `Package.resolved`: XcodeGen → Xcode/xcodebuild; Swift 5 language mode, SwiftUI, AppKit, Combine. Deployment target в конфигурации — macOS 15. README и комментарии CI местами упоминают macOS 26: документацию нужно согласовать и проверить минимальную ОС сборкой.
- Внешние SwiftPM-пакеты: Sparkle и SwiftNIO; lockfile также содержит swift-atomics, swift-collections, swift-system. Есть встроенный C-декодер zstd для кэша Claude Desktop и обращения к системным Security/SQLite/WebKit.
- `windows/`: самостоятельное приложение Rust 2021 + Tauri 2/WebView2, HTML/CSS/JS без отдельного React-фронтенда. Cargo workspace, отдельный `codenotch-hook`, NSIS-упаковка, Rust-тесты и JS-проверки. Общего исполняемого UI-кода со Swift-версией нет.
- `.github/workflows/`, `Scripts/`, `site/`: внешняя CI/release-инфраструктура, signing/notarization, appcast; в `site/` также лежит готовый DMG.

## Подтверждённые поверхности интеграции

### Внешние API и чужие credentials

`AppDelegate.swift` собирает множество провайдеров: Claude, Cursor, Codex, Antigravity, GLM, MiniMax, Grok, Devin, OpenCode, GitHub Copilot и другие, включая локальные runtime и произвольные endpoints.

Примеры из исходников:

- `CodexLocalProvider.swift`: читает credentials, обращается к `https://chatgpt.com/backend-api/wham/usage`, запрашивает дополнительные данные. Слово Local не означает отсутствие сети.
- `CursorCredentials.swift`: читает `state.vscdb`, конфигурацию CLI и Keychain; `CursorLocalProvider.swift` обращается к `https://cursor.com/api/usage-summary`.
- `KeychainPrompt.swift` и credential-модули: доступ к секретам сторонних приложений.
- `WebSessionProvider.swift`, `Sites.swift`: вход через WKWebView и web-сессии провайдеров.
- `CustomEndpointProvider.swift`: универсальные URL и ключи, запросы usage и `/models`. Это не готовый минимальный корпоративный адаптер.

### Команды, процессы, файлы агентов

`ClaudeUsageCLI.swift`, `ClaudeTokenRefresher`, `KiroCLI.swift`, `TerminalCommand.swift`, session-мониторы и focus-механизмы выходят за пределы простого отображения чисел. Есть чтение локальных данных сессий, запуск CLI и управление фокусом других приложений.

В комментарии `ClaudeUsageCLI.swift` прямо объясняется, что телеметрия запускаемого Claude CLI намеренно не отключается ради feature gates. Это свидетельство дополнительного пути сетевой активности через дочерний процесс, а не доказательство отдельного аналитического SDK внутри Codenotch. Полное отсутствие телеметрии статическим поиском не установлено.

Windows содержит установку hooks в `~/.claude/settings.json` (`hooks_install.rs`), HTTP-приём событий (`server.rs`), watchers и взаимодействие с процессами.

### Серверы и обновления

- `PhoneLinkServer.swift`: SwiftNIO-сервер, рассчитанный на private-network адреса и loopback. Сейчас `PhoneLink.isAvailable = false`; наличие кода не означает, что он слушает порт в этой версии. Для минимальной поставки удалить полностью.
- `OllamaRelayServer.swift`: отдельный loopback-сервер, подключаемый через Ollama relay.
- `Updater.swift`, `project.yml`: Sparkle, feed `https://hivinz.com/appcast.xml`, настройки автоматических проверок/обновлений.
- Windows `main.rs`: регистрация updater, проверка при запуске, запуск server и watcher. Updater endpoint задан в `tauri.conf.json`; разрешение есть в capabilities.
- Windows `tauri.conf.json`: `csp: null`. Если Windows остаётся, задать и проверить ограничивающую CSP для локального UI.

### Хранение и сборка

`UsageArchive.swift` сохраняет последние показания и дополнительные данные в UserDefaults. `Preferences` мигрирует настройки старого приложения. Для корпоративной версии нужны отдельный bundle ID и чистое пространство настроек без импорта прежних аккаунтов, URL и кэшей.

В `project.yml` выключен App Sandbox; присутствуют идентификаторы и signing team исходного проекта. Публичные CI, загрузка зависимостей и release-публикация — отдельная поверхность, даже если runtime больше не использует сеть.

## Целевая архитектура

`DemoUsageSource → минимальный UsageStore → нейтральный UsageSnapshot → Notch + карточка + меню`

Позже `DemoUsageSource` заменяется одним корпоративным источником через узкий интерфейс чтения снимка. UI не знает о токенах, HTTP, CLI, сторонних аккаунтах и sign-in.

Оставить:

- Геометрию notch, размещение, анимации, кольца, краткую карточку, выбор экрана, масштаб и оформление.
- Нейтральную модель: название лимита, единица, использовано/всего либо подтверждённая доля, время сброса, время получения, состояние данных.
- Состояния «нет данных», «устарело», «ошибка»; отсутствие данных не превращать в 0% использования.
- Локальные настройки внешнего вида. Уведомления — отдельное решение; начальный UI может обойтись без системных уведомлений и звуков.

Убрать аккаунты, login/logout, команды установки, внешние ссылки, выбор провайдеров, session activity, историю токенов, модели локальных runtime, импорт иконок и произвольные endpoints. Функцию скрытия по активности чужих окон также можно исключить из первого минимального варианта.

## Порядок работ

### 1. Зафиксировать границы

Определить минимальную версию macOS и обязательные UI-функции. Зафиксировать модель угроз как перечень запрещённых возможностей: исходящая сеть, listeners, чтение чужих credentials/сессий, subprocess, запись в настройки агентов, self-update. Инвентаризацию проводить по исполняемым путям, отдельно от URL в комментариях и лицензиях.

Результат: согласованный набор возможностей и воспроизводимая исходная точка.

### 2. Создать минимальную точку запуска

Заменить orchestration в `AppDelegate.swift` на создание окна, нейтральной модели и демонстрационного источника. Перенести нужные общие типы из Providers. Упростить `UsageProvider` до интерфейса получения показаний без account/signIn/signOut; упростить либо заменить UsageStore.

Не использовать `CODENOTCH_DEMO=1` как границу безопасности: переключатель меняет источник отображаемых снимков, но не завершает весь путь запуска, а обнаружение профилей находится в свойствах AppDelegate.

Результат: notch работает на явно обозначенных демоданных без создания интеграционных объектов.

### 3. Удалить интеграционный код и зависимости

Удалить провайдеры и credentials, Sessions, PhoneLink, Updater, TerminalCommand, custom endpoints и соответствующие callback/settings/UI-пути. Проверить оставшиеся зависимости TooltipCard, NotchViewModel, StatusItemController и SettingsView от удалённых типов.

После удаления потребителей убрать Sparkle, SwiftNIO и их транзитивные пакеты, zstd и bridging header. Проверить отсутствие оставшихся потребителей SQLite/WebKit/Security. Удалить ненужные provider assets и строки локализаций, сохранив лицензии используемых ресурсов.

Результат: минимальный macOS target без сторонних SwiftPM-пакетов — достижимая цель по текущему составу зависимостей, подтверждаемая сборкой.

### 4. Очистить поставку

Сократить Preferences и архивирование; по умолчанию не сохранять историю лимитов. Задать отдельный bundle ID, исключить миграцию старых настроек. Убрать SU-настройки и описание доступа к локальной сети. Включить App Sandbox и проверить работу окон без сетевых entitlements, Apple Events и доступа к чужим файлам.

Переписать Makefile и build-конфигурацию под согласованный способ подписи и внутреннюю доставку. Убрать публичные release workflows, appcast, готовый DMG, ненужные scripts и сайт из корпоративной поставки. Не отключать системные проверки установки; способ подписи определяется процессом организации. Сохранить MIT/third-party notices на оставшийся код и ресурсы.

Удалить Windows-порт (`windows/`) и его workflows из итогового минимального дерева. Переносить или дорабатывать Rust/Tauri-реализацию в рамках этой задачи не требуется.

### 5. Проверить автономный UI

- Сборка и релевантные тесты геометрии, процентов, reset-time, пустых/устаревших данных; удалить тесты удалённых интеграций.
- Статическая проверка оставшихся сетевых клиентов, listeners, subprocess, credential APIs и внешних ссылок. Проверка только строк URL недостаточна.
- В изолированном окружении проверить холодный запуск, настройки, все кнопки, сон/пробуждение и работу дольше фоновых интервалов: нет инициируемых приложением исходящих запросов и listeners, дочерних CLI, чтения чужих auth/session-файлов или записи в настройки агентов. Учитывать дочерние процессы/WebView, если остаются.
- Проверить manifest, зависимости и содержимое собранного пакета; отсутствие Sparkle/helpers и ненужных библиотек, отсутствие старого updater feed.
- Проверить запуск после наличия старых настроек: они не включают скрытые интеграции.
- Проверить сборку без обращения к публичным реестрам при заранее подготовленном утверждённом toolchain. Runtime-offline и сборка без внешней сети — разные критерии.

Результат: автономный UI и краткий протокол проверок. Это техническое основание для внутреннего рассмотрения, не утверждение о соответствии неизвестным требованиям банка.

### 6. Подключить реальные корпоративные лимиты

Только после определения поддерживаемого источника. Предпочтительный минимальный вариант — чтение документированного файла со снимком, который предоставляет сам корпоративный агент или утверждённый компонент. Отдельно согласовать формат, доступ, размер, обновление, TTL и единицы. Не создавать скрытый helper, продолжающий старые внешние интеграции.

Если доступен только внутренний API — один фиксированный клиент с утверждённой аутентификацией, ограниченным адресом, проверкой TLS, запретом неожиданных redirects, timeout/backoff и без универсального редактора URL. При смене источника/учётной записи старые показания не должны приписываться новой.

Проверить: реальная квота или оценка, индивидуальная или командная, used или remaining, окна/reset/timezone, поведение при недоступности и отсутствие секретов в логах. Не выводить лимит из простого расхода токенов без подтверждённой модели расчёта.

## Что требуется уточнить перед реализацией

1. Минимальная версия macOS на рабочих машинах; сама платформа уже выбрана.
2. Как называется корпоративный агент и где он официально предоставляет лимиты: файл, CLI, внутренний API, другое. Секреты для ответа не нужны.
3. Достаточно ли notch с процентом и временем сброса; нужны ли меню, несколько экранов и уведомления.
4. Есть ли утверждённые ограничения на зависимости, sandbox, подпись и доставку. До получения ответа проектировать первый результат полностью автономным.
